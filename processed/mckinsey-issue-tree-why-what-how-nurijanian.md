# /mckinsey-issue-tree: trees to solve any problem

@nurijanian (George / prodmgmt.world) on why product work fails *before* analysis: teams mix **cause**, **plan**, and **solution** in one fuzzy question. Fix: pick one MECE “issue tree” path and stick to it.

## Three trees

| Tree | Root | Leaves / output |
|------|------|-----------------|
| **Why-tree** | Why is this happening? | Cause families → **testable hypotheses** |
| **What-tree** | What work does this deliverable require? | Evidence, decisions, commitments, synthesis → **sequenced workplan** |
| **How-tree** | How might we achieve this goal? | Concrete interventions → **ranked options** |

Rule of thumb: Why = causes, What = work units, How = actions. Different leaf types support different decisions.

## Activation example (placeholder branches)

Input: new-user activation underperforming; need to decide what to do.

- **Why** first if the cause is unknown.
- **What** if the job is to produce an activation plan (analysis → decisions → commitments → synthesis).
- **How** once causes are confirmed (interventions tied to confirmed causes / constraints).

## Workflow

1. Name the real need: causes, a plan, or options.  
2. Choose Why / What / How.  
3. Build first-level branches.  
4. MECE check: one missing branch + one overlapping branch before trusting the tree.  
5. AI drafts and checks structure; PM owns problem framing and judgment.

Teams should not hand-build process each time — make it a **repeatable skill** so AI does repetitive structuring/validation.

## Skeptical read

Product pitch: `mckinsey-issue-tree` as one of 243 PM skills in **AI PM OS** (Claude Code / Cowork / Cursor), $499/yr for up to 10 PMs. The Why/What/How split stands without the product. Enterprise reply risk (not in raw body but common): trees need ownership, evidence versioning, and decision authority across orgs or they re-create ambiguity.
