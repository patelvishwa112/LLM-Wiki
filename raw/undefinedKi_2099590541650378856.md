Eval engineering, explained like you're five. Everyone is talking about it and almost nobody can define it.

The model does the work, but someone has to say "this is right." As long as that someone is you, the agent cannot run without you. Eval engineering is writing down what "right" means so a machine can check it instead.

Without it, change a prompt or swap a model and you have no way to tell whether you broke something.

Here is how to build one.

Start with your failures.

Pull a hundred real failed runs and read them by hand. Write what went wrong in your own words, then group the lines. Three or four failure types will cover most of it, and they will not be the ones you expected.

This is why generic judges do not work. Hamel Husain's example: a judge scoring "helpfulness" passed an answer that connected a bathroom to the wrong place.

Then build checks in two layers.

Code first, because it is free and gives the same answer every time:

> does it parse
> does it compile
> is the field present
> does the number have a source

Then a model as judge, only for what code cannot cover. One thing to decide per judge, and yes or no rather than one to five.

Before trusting it, feed it examples you labelled yourself. If it disagrees with you, fix the rubric, not the agent.

Two or three code checks and one or two model checks is a complete suite.
