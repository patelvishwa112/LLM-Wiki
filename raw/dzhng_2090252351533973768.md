The amount of code being written today far outpaces our ability to review it. That part isn't controversial. What's more interesting is that we're visibly losing — the amount of AI slop in modern codebases right now is insane, and AI coding is obviously not going away. So which is it? Do we just embrace the slop, or is there a way to have our cake and eat it too?

I think there's a way out. But it requires giving up something most of us aren't ready to give up yet.

Slop is not a model quality problem. SOTA models have more or less mastered writing code (coding vs engineering). Slop is what happens when generation is unbounded and verification is bottlenecked on a human reading the output.

Code gets generated faster every quarter. The review step runs at a fixed human rate. When supply massively exceeds inspection capacity, inspection stops being a filter and becomes a formality. You skim. You approve. LGTM becomes the default, quality drifts toward whatever passes a skim.

If the goal is still to read every line, we are bottlenecked by our own ability to review, and quality degrades toward zero. Embrace the slop and you've accepted the degradation. Slow down generation to match your reading speed and you've thrown away the entire advantage. The only move left is to stop making human reading the bottleneck.

It gets worse: the code is going to stop being readable. Right now AI still writes human-readable TypeScript and Python. That may not last — Claude-speak, AI-native languages, or direct machine code. More AI reviewers pinned to the artifact get less relevant as the artifact goes opaque.

The job was never writing code. Engineering is about solving problems. A programmer's output is code; an engineer's output is a solved problem. The future is the system by which you work with AI: what gets specified, what gets delegated, what gets verified, and how you know when to trust it. That system is the deliverable now.

The entire SDLC assumes you can read the code. PRs, review, approvals, linters, style guides. If that assumption breaks, patching the process doesn't help.

You already ship code you don't read. Dependencies and their dependencies round to zero percent read. A VP of Eng is accountable without reading. Responsibility required knowing the system was structured so that problems surfaced. The new thing is that unreadability is reaching first-party code.

Treat the codebase as a black box. Stop treating this as a code review problem. Treat it as an interpretability problem.

Structure the codebase into extremely domain-specific pieces with well defined inputs and outputs. Attach sensors. Run the functions. Examine the outputs. Build trust by constantly interrogating it — every new user journey, every edge case. Never read the implementation. The interface becomes the review surface.

Artifacts that must stay readable no matter what the code compiles down to:
- Invariants: what must always be true, in a form you can check
- Traces: what actually happened on a real run, at the seams
- Attack surface: what this piece is exposed to and allowed to touch
- Decisions: every choice made where the spec was silent

These are living artifacts, not traditional specs.

Behavior tells you what. It doesn't tell you why. Sensors go green while the agent silently picked optimistic concurrency, invented a retry policy, or shared a table. Those decisions bite three months later.

Whenever a coding agent session runs, a skill should hand back a ledger of every decision where the spec was silent — plain language, ranked least-confident first. A two-day run produces tens of thousands of lines never audited, and maybe thirty decisions that determine whether the thing is right. Read the thirty. Push back on four.

That is what good senior review always did: catch the wrong abstraction, not nitpick lines.

Auditor must be a separate pass from the implementer (independent sub-agent). A model reviewing its own work rationalizes. The audit never blocks and cannot change code, or it optimizes for a clean report.

Intent going in, behavior coming out, implementation free to be unreadable in between.

The usual objection: a compiler is deterministic, AI is probabilistic. What is being replaced is the person who typed the code, who was never deterministic either. Review, tests, and staged rollouts existed because that step was unreliable. They don't stop working because it got a thousand times faster.

The hard part is the slicing. Independently verifiable pieces: build, instrument, and be wrong about in isolation. Before you slice you have to know the shape. Treat it as fog of war. Scout before you plan: known / unknown / blindspot, rendered options and decision tables. Carve territories. Re-slice when a territory hides more map.

One unattended run pursuing a single goal for 1 day, 16 hours — slicing, building, verifying, re-slicing. Reviewed the ledger, not the diff.

The loop:
1. Map the fog
2. Codify the spec
3. Build in loop mode; reviews fire per slice; re-slice when stale
4. Review the ledger, least-confident first

Narrower claim: if human reading of the artifact stays the verification step, slop is guaranteed. Software factory = production line where intent and behavior are the inspected outputs, and the code is what falls out the end.
