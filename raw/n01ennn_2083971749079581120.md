## Core thesis
Memory engineering is a distinct discipline for AI agents — not just retrieval or vector DBs, but a full system managing cost, utility, control, and hardware. Problems are less "forgetting" than never forgetting on purpose while ignoring write-path cost, stale data, and KV/HBM pressure.

## Four lab lenses
1. Stanford — What does remembering cost? (write path, energy per correct answer; systems can differ ~47x in cost at same accuracy)
2. Microsoft — What is worth keeping? (facts and skills not raw logs; utility density; model-managed context; forgetting leaves shadows)
3. Anthropic — Who controls what it keeps? (file-based memory the agent can read/write/delete; audit, export, scope, rollback)
4. Nvidia — Where does it hit hardware? (KV cache in HBM; memory construction as background/prefill job; rate-limit/batch)

## Build order (selected steps)
- See memory as metabolism (energy, growth, rot), not passive storage
- Price write path before building; measure energy per correct answer
- Store facts/skills; optimize utility density not volume
- File-backed controllable memory with delete and audit from day one
- Hardware: treat construction as background; free KV slots; tokens/s
- Prove passes by hand on real history first
- Forgetting policy (dedup, consolidation, rules) before store grows; never auto-merge contradictions blindly
- Ship order: write path → contradiction detection → forgetting → hardware tuning

## Closing
Run manual passes until they change decisions; treat memory as engineered lifecycle+cost, not an ever-growing bucket.
