Recursive Self Improvement
Recursive self-improvement (RSI) is the idea that an AI system that gets better at the process that makes it better. That improved process then gets applied again, to produce an even more capable system, which improves the process again, and so on. It's improvement that feeds back into itself. Hence, the term "recursive".
In other words, each improved system further improves the process that produces its successors

This is an old idea, by the way, even though it has recently become a buzzword in AI circles. You'll see this traced back to I.J. Good's 1965 speculation about an "intelligence explosion," and it's been kicking around in AI safety and forecasting circles for decades. What's changed recently is that it's stopped being purely a thought experiment, because LLMs have shown excellent coding capabilities. 
LLMs can write code, run experiments, and read their own error logs. Add to the fact that there is a shitton of money being funded into AI research right now. So the RSI idea has, for the first time ever, plausible for researchers to actually pursue.


RSI vs Meta Evolution
There are three tiers of self improving AI. A ladder if you will. Roughly, here they are arranged from least complex to most complex.
Evolution / search: an AI generates and mutates candidate solutions, but the thing doing the searching stays fixed and untrained. Example: AlphaEvolve, GEPA
Meta-evolution: the searcher itself, i.e. the operators that generate and mutate solutions, gets trained on feedback from past search. The improver is now a learned artifact, not a fixed algorithm. Example: Frontis-MA1 (this paper).
Recursive self-improvement: that trained improver is used to improve the next improver, and the loop closes on itself indefinitely.
In this context, operator refers to "modes" of operations. Skills or options if you will. Let's discuss it next.


How Evolutionary LM is Trained
Training a system for recursive self-improvement (RSI) doesn't require solving the full, open-ended version of the problem in one shot. One workable strategy is to pick a narrow-but-scoreable domain (in this case, machine learning engineering, since every candidate solution can be executed and scored objectively), and design a training loop where the model's own transformations to a solution become the training signal. 
Frontis-MA1 is just one concrete model trained via this recipe; BUT the recipe itself is domain-general as long as a candidate solution can be faithfully benchmarked.
These are some good to have things before you start training RSI
A verifiable execution environment. Every candidate "solution" the model produces must be automatically executable and scoreable. No human-in-the-loop judgment.
A quality-filtered task distribution. The tasks themselves need to be validated. Not stupid, not degenerate, not trivially solvable, not leaking test labels, and appropriately difficult.
A small, reusable "skills" instead of full trajectories. Rather than trying to imitate or reward entire multi-step search episodes end-to-end (which gives extremely sparse, hard-to-credit-assign supervision), can we decompose the agent's behavior into atomic steps that can each be trained independently and then composed at inference time. The Frontis paper calls this "operator vocabulary" coz its a collection of skills that the model learns to perform.
The Training Loop
Let's look at exactly how the Frontis-MA1 model is trained. 
They train 4 different operators:
Draft: Generates a brand-new candidate program from scratch (no parent)
Improve: Takes an existing (parent) program and modifies it to boost performance
Debug: Takes a broken/erroring program and repairs it using the error signal
Crossover: Combines two parent programs, recombining their complementary strengths
All four operators — Draft, Improve, Debug, Crossover — share the same underlying harness:
The same base model​ generates code in all four cases.
The same sandbox execution backend runs and scores whatever program comes out.
The "action" in every case is the same: produce a Python program.
Even the system prompts are similar. E.g., "You are a Kaggle Grandmaster attending a high-stakes competition... come up with an excellent and creative plan... implement this solution in Python," 
Where they differ is the context that gets sent in. For example:
Draft: Only the task specification (no parents)
Improve: The parent, its 3 most recent ancestors, and top 3 ranked siblings, etc
Crossover: Context about each selected parent
Debug: Context about the current buggy node, error signatures etc.
At each step t of a search episode, the algorithm:
Selects an operator​ (e.g. Improve),
Constructs an operator-specific context​ from zero or more parent programs and their execution history,
Samples a candidate program from the policy... The LM-to-be-trained generates a python program
The python program is executed in the sandbox
The execution is then scored.
Every executed program and its outcome gets stored in a task-local program database, and the evolutionary search tries to find the candidate maximizing the score within a fixed compute budget
Note how both training and inference share the same operator interface. The thing you fine-tune (a language model that writes python program to do AutoML) is exactly the thing the search loop calls at inference time.
Step-by-Step: How the Model Evolves
Step 1) Supervised Warm Start (SFT)
Before any reinforcement signal is useful, the base model needs to reliably produce valid, executable programs for each operator. This stage:
Samples many candidate programs per task,
Actually executes them in the sandbox,
Keeps only the ones that are valid and score well, using a difficulty-aware rejection strategy — stopping early on easy tasks once enough good examples are collected, and spending more budget on tasks where successes are sparse.
This produces positive-example pairs used for standard supervised fine-tuning: maximize the likelihood of high-scoring programs under gθgθ​ 15. This is the "warm start" — it gets the model minimally competent at each operator before RL begins.
Step 2) Reinforcement Learning on Execution Reward
Once the model can reliably produce valid programs, RL squeezes out further quality using the actual sandbox score as reward. You can read the paper for all the details of how the RL environment/training is done, like reward normalization and asynchronous rollouts (very common practice in labs currently https://x.com/neural_avb/status/2022715561390776524?s=20)
Even during RL, the algorithm has to decide which program states to practice operators on. It uses a fitness-proportional utility to exploit strong existing programs, targeting states where outcomes are still uncertain (high child-reward variance — where there's real learning signal), and a cooling term to avoid over-training on one incumbent solution
Step 3) The Long-Horizon Evolutionary Search
This is where "evolution" becomes "meta-evolution": the now-trained operators get deployed inside a population-based search harness at inference time.
Basically, you attach multiple numerical scores to every experiment attempt.

You maintain a population of such experiments.

Then you pick out candidates to mutate and train on.
Structured experience accumulation: every evaluated candidate becomes a "experience card" (provenance, score, error type, resource usage), and all cards aggregate into a task-global "experience board" tracking method families, best-per-family results, underexplored directions, and repeated failures.
Experience-guided parent selection: instead of picking the next node to expand purely by raw fitness (which over-concentrates search on already-strong nodes), selection also looks at other stats (such as improvement over parent, and method novelty) so the search doesn't get stuck exploiting one local optimum.
On-demand memory synthesis: rather than wastefully summarizing every node with an LLM call, natural-language memory is only synthesized after an operator has selected which parent(s) it needs, and only for those selected nodes and their relevant neighbors.
Operator-conditioned context construction: As discussed earlier, each operator gets a different, bounded slice of context. Improve sees ancestor lineage plus sibling contrasts; Crossover sees both parents plus a complementarity cue; Debug retrieves prior attempts with the same error signature. Etc


The missing "recursive" piece, distinguishing meta-evolution from RSI proper)
The paper is explicit that this is a step toward meta-evolution, not full RSI.
Quoting directly: 
meta-evolution closes an additional learning loop by reusing these evolutionary trajectories to train the model that proposes future modifications... RSI requires a stronger and sustained loop in which each upgraded system further improves the process that produces its successors
