# A Practical Guide To The 3 Layers People Keep Mixing Together

Most people talk about AI agents as if they are one thing. Once an agent moves beyond toy demos and starts touching files, APIs, documents, customers, or production code, you are no longer just "prompting a model." You are designing a system.

Three concepts constantly get conflated:
- Agent harness engineering
- Loop engineering
- Graph engineering

They all sit around the same model and affect reliability, but they solve different problems. Mixing them up leads to debugging the wrong layer.

## The 30-Second Distinction
- Harness engineering builds the environment around the model (tools, memory, persistence, safety, observability).
- Loop engineering designs the repeated work-and-feedback cycle (retry logic, verification, evidence-based stopping conditions).
- Graph engineering makes the workflow topology explicit (what steps are allowed next, branching, handoffs, approvals).

Mental model: Environment → Feedback → Flow

## 1. Harness Engineering
This is the "operating system" for the model. A raw model cannot maintain state, safely call tools, enforce permissions, or recover from failures — the harness provides all of that.

Typical components:
- Context injection (instructions, memory, policies, retrieved knowledge)
- Action surfaces (APIs, browser, code execution, databases, MCP tools)
- Persistence (files, checkpoints, git history, long-term memory)
- Execution control (retries, timeouts, budgets, model routing, approvals)
- Safety/governance (least-privilege permissions, isolation, secret handling)
- Observability (traces, logs, eval results, cost/latency tracking)

When to focus here: The agent cannot operate reliably, loses context, has permission issues, or cannot be audited. Different harnesses on the same model produce wildly different results.

## 2. Loop Engineering
Every tool-using agent has a basic loop (call model → run tools → feed observations back). Loop engineering intentionally designs better cycles around that.

Key elements of a good loop:
- Clear trigger
- Specific success goal (not vague "improve")
- Required state for the next cycle
- Action policy
- Evidence requirements (tests, validation, reviewer approval — not just model confidence)
- Compact, actionable feedback
- Explicit stop rules (success, timeout, budget, max retries, escalation)

Core principle: Do not loop on confidence. Loop on evidence.

Loop engineering is not prompt engineering. Prompting improves a single response. Loops improve a repeatable, verifiable process.

## 3. Graph Engineering
This makes workflow structure explicit. Instead of ad-hoc code, you define nodes (steps), edges (transitions), branching, parallel work, joins, retries, and human gates.

What graph engineers design:
- Node boundaries (LLM call vs deterministic function vs specialist agent vs human review)
- State schemas
- Routing conditions based on evidence
- Concurrency rules
- Cycles, exits, and durability/checkpoints

Use graphs when: You have meaningful branching, approvals, specialist handoffs, parallel work, recovery paths, or complex multi-step processes. For simple "give one agent tools and let it run," a strong harness + loops is often enough.

## How They Work Together (Example: Research-and-Publishing Agent)
- Harness: Browser, search tools, file workspace, memory, citation tools, approval gates, traces.
- Loop: Retries weak sources, fixes citation failures, runs grader checks, refreshes on market changes.
- Graph: Explicit path (scoping → research → screening → synthesis → drafting → legal review → publication) with human gate before release.

## Practical Diagnosis Rule
- Agent cannot operate → Fix the harness.
- Agent almost works but is unreliable → Fix the loop (evidence, retries, stop conditions).
- Process is complex with many paths/stakeholders → Fix the graph.

## Common Mistakes
- Building elaborate graphs before validating basic harness + loops.
- Letting the same model write and grade without safeguards.
- Using "keep trying" as a loop (creates uncontrolled cost).
- Treating the harness like a junk drawer (too many tools = noisy context and errors).
- Blaming the model for orchestration failures.

## Final Takeaway
The real differentiator in production agents is not the model — it is the system around the model.
- Harness makes the model operational.
- Loops make the work iterative and verifiable.
- Graphs make execution explicit and controllable.

None replaces the others. Reliable agent systems emerge when all three layers are designed intentionally.
