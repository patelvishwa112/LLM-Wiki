## Post

Frontier models have converged on million-token context windows. GLM-5.2, Deepseek-v4, MiniMax M3, Kimi K3, and Thinking Machines' Inkling all shipped 1M windows within the last two months, and the pull is coming less from longer documents than from agents - involving multi-hour coding sessions, extensive tool call and preserved reasoning traces, and large repositories held in working memory.

The bill for all this lands in a specific place. Beyond quadratic prefill, the dominant constraint in long-context serving is the KV cache. Decode is memory-bandwidth-bound: to produce each new token, the model reads its entire cached key-value history out of HBM, and that cache grows linearly with context length and again with batch size. The numbers get uncomfortable fast. Take a toy frontier-scale config: a 1T-parameter model with 100 layers, using GQA with eight KV heads at head dimension 128. The cache works out to roughly 0.4 MB per token. A 128K-token request carries about 50 GB of cache, and a 1M-token request over 400 GB (five H100s' worth of memory for a single conversation) before a single model weight is loaded. And every byte of it is re-read for every token generated, so even spreading that read across a full eight-GPU node caps decode at quite low tokens/second. The GPU ends up spending most of its time waiting on memory rather than computing.

Sparse attention is the lever this generation has leaned on hardest, and the past year produced a wave of it with DeepSeek's DSA, MiniMax's MSA, and a handful of related designs. I wanted to write down how the pieces fit together, partly to organize my own understanding, partly because I think the through-line is easy to miss if you read each paper in isolation.

The question underneath all of this work is how do you stop reading everything on every token? The specific designs differ across many details, but one lens separates them cleanly: Who decides what each query attends to, and at what granularity?

## The design space

The earliest answer, which predates the recent long context era, is to shrink the cache by sharing it. Standard multi-head attention gives every query head its own keys and values. Multi-query attention (MQA) collapsed all the KV heads into one, which saved a lot of memory but cost quality [1]. Grouped-query attention (GQA) split the difference by letting groups of query heads share a KV head, and it worked well enough that it's now the unmarked default [2].

Head sharing only buys a constant factor though. The cache still grows with every token, and each query still reads all of it. Pushing further means changing either what attention stores or what it reads, and the designs for this sort into three key axes:

- **Compress the cache.** Share KV heads (MQA, GQA), or project keys and values into a low-rank latent space, like DeepSeek's MLA [3], which caches a single small latent per token instead of full per-head keys and values and expands it back at compute time. Every query still sees everything, "everything" is just smaller.
- **Restrict the pattern.** Each query attends to a subset of positions. This ranges from static (sliding windows, global tokens, fixed at design time) to learned, where a trainable module decides per query what matters.
- **Replace the primitive.** Linear attention, state-space models in the Mamba family, recurrence. Constant-size state, no cache growth at all.

Most of the 2025–26 story is about the second axis becoming learned. To understand why the field moved there, it helps to watch one lab's journey along the third axis first.

## MiniMax's arc, and the fork

MiniMax initially bet aggressively on linear attention. MiniMax-01 (January 2025) and M1 (June 2025) were enormous production deployments of a linear hybrid, applying Lightning Attention interleaved with softmax layers trained out to 1M context [4]. For a while this was the existence proof that the third axis could actually ship at frontier scale.

Then M2 came out in October 2025 with plain full attention, and MiniMax published an honest post explaining the reversal [5]. While their small-scale hybrid experiments had looked as good as full attention on the benchmarks at the time, the deficits only showed up at scale, and specifically on complex multi-hop reasoning, the types of workloads that now matter most. The conclusion was roughly that efficient attention still has some way to go before it can definitively beat full attention in a real industrial system.

I don't read this as "linear attention is dead," though. What happened next looks more like a fork. On one side, DeepSeek and later MiniMax again, went to learned sparsity over softmax attention, keeping the exact primitive but learning what to skip. The other side doubled down on linear/full hybrids, and the workhorse there is DeltaNet. Linear attention replaces the growing KV cache with a fixed-size matrix memory that every new token gets folded into. Its classic weakness is interference where new writes pile onto old ones causing the state to get muddy. DeltaNet writes more carefully, as before storing a new value under a key, it first subtracts whatever the memory currently holds for that key so that the state gets edited rather than accumulated. Gated variants add learned forgetting on top, as adopted by Qwen3.5, which runs three Gated DeltaNet layers for every full-attention layer [6]. Moonshot built Kimi Delta Attention (KDA), a DeltaNet variant with finer, channel-wise gating so each feature dimension can forget at its own rate, interleaved it 3:1 with full MLA layers, and reported it beating full attention under matched training while cutting KV cache use by up to 75% [7]. The recent release of Kimi K3, shipped on KDA with a 1M window, proves this direction in production [8].

The rest of this post follows the sparsity branch, where two labs starting from different substrates converged on a very similar recipe.

## The template: NSA

The recipe has a common ancestor in DeepSeek's Native Sparse Attention paper from February 2025 [9]. Two case studies that follow descend directly from it, so it's worth a short summary of what it proposed.

NSA runs three parallel attention paths for every query. A compression branch attends over coarse block-level summaries of the context, cheap and global. A selection branch picks the top-scoring blocks and attends to their raw tokens, precise but sparse. And a sliding-window branch handles local context. A learned gate mixes the three outputs per head. The design is deliberately hardware-aligned as it operates at block granularity such that the memory access patterns stay contiguous and tensor-core friendly.

But NSA's more lasting contribution is an argument about training. If you train a model dense and impose sparsity only at inference, the attention heads that learned to do retrieval under dense training get scrambled, because the tokens they relied on are suddenly missing. So sparsity should enter the gradients, ideally from the start of pretraining.

NSA served as a starting template for many following methods, where each successor essentially kept the branch it believed in and removed the rest.

## DSA case study: compress, then select tokens

DeepSeek Sparse Attention shipped in V3.2-Exp in September 2025 [10], and it stacks the first two axes on top of each other. The substrate is MLA, so the cache is already compressed into latent vectors. On top of that sits what they call a lightning indexer, a small scoring module with only a few heads, ReLU instead of softmax for throughput, and an FP8 implementation, which computes an index score between the current query and every cached token. This keeps the top 2,048 tokens by score and runs exact attention over just those while discarding the rest. Attention complexity drops from O(L²) to O(Lk). The indexer itself is still O(L) and is sufficiently light that this doesn't dominate.

There's a subtle kernel-level reason DSA is instantiated in the MQA mode of MLA. That is, each compressed latent entry gets shared across all the query heads of a token, which is what makes the memory arithmetic work out when gathering scattered tokens [10].

Two things about DSA stand out most. The first is granularity. Selection is per token, so nothing gets included or dropped because of which block it happens to live in. The second is that the whole thing was initially a retrofit. DeepSeek originally didn't pretrain from scratch; they took the finished V3.1-Terminus checkpoint and continued training with the indexer bolted on. The fact that you can graft a sparse pattern onto a trained dense model and keep quality basically intact was a real result on its own. DSA has since been adopted by models such as GLM-5, which runs it on top of MLA, while GLM-5.2 extends it with IndexShare applying one indexer serving every four layers instead of one per layer [6][11].

## MSA case study: select blocks, keep everything else standard

MiniMax's return to efficient attention came with M3 in June 2026, and the design is essentially a stripped-down NSA [12][13]. Of NSA's three paths, MSA drops compression and the sliding window, and keeps only selection. The substrate is plain GQA rather than MLA, and the KV cache stays uncompressed.

What remains is two components. An index branch, which adds exactly two projection matrices to standard GQA, scores the KV cache in 128-token blocks using max-pooled scores, and keeps the top 16 blocks per query, always retaining the most recent block for training stability. Then the main branch runs exact softmax attention over the tokens in those blocks. That maintains fixed budget of 2,048 KV tokens per query whether the context is 10K or 1M [13].

Three choices distinguish MSA from DSA. MSA selects at a coarser block level, so every read is 128 contiguous tokens, a unit that GPU memory streams efficiently. Selection per GQA group, as each KV-head group picks its own blocks independently, so different groups can retrieve different parts of the context while execution stays block-level. Finally, MSA deliberately skips the cache shrink that MLA provides, betting that full-precision retrieval from deep context matters more than the memory savings.

## Inkling case study: nobody decides

For contrast, Thinking Machines' Inkling (July 2026, 1M context) uses no learned selection at all [14]. The decoder interleaves sliding-window and global attention layers at a 5:1 ratio, with a 512-token window on the local layers. The pattern itself is well-established. Mistral 7B popularized the sliding window, GPT-OSS alternates local and dense layers one-to-one, and Gemma 3 runs the same 5:1 interleave as Inkling, just with a 1024-token window rather than 512. Inkling is the largest open model yet to lean on the pattern. To compensate for that aggressive locality, every layer applies short causal convolutions in four places: on the key and value streams before attention, and on the attention and MLP outputs before they rejoin the residual stream [14][15]. The sconvs themselves aren't a sparsity mechanism but rather they're cheap local token mixing, in other words a built-in bias toward short-range structure that gives back some of what the narrow windows take away.

The structural difference from DSA and MSA is per-layer versus per-token sparsity. Inkling's global layers are still fully dense, so per-query cost at 1M is not flat. The savings come from making five-sixths of the layers cheap, not from bounding what any individual query reads. In exchange you get a much simpler contract with no indexer to train, no routing to stabilize, and simpler failure modes to reason about. The bet is that a periodic dense layer integrates whatever the windows miss.

Whether that holds at long agentic horizons, where the token you need is 700K positions back and the next global layer is four layers away, is where the learned-selection camp is betting differently.

## Training a router you can't backprop through

This is the section where DSA and MSA are nearly the same.

The problem is that top-k selection is non-differentiable. The typical language model loss can't teach the indexer anything, because gradients don't flow through a hard cutoff over tokens or blocks. So how does the selector learn what matters?

Both labs answer with a form of self-distillation. The indexer trains against a KL loss that aligns its scoring distribution with the main branch's own attention distribution. Dense attention is the teacher, the sparse selector is the student, and both live inside the same forward pass. In MSA's version the teacher is the group-averaged main-branch distribution over the selected tokens [13]; DSA sums attention scores across heads and L1-normalizes to build its target [10].

Both also apply a stop-gradient at the same place, detaching the indexer's input so the KL loss trains only the indexer projections and never touches the backbone. The main model sees only the language model loss. MiniMax reports that without the detach, larger KL coefficients caused gradient spikes and outright divergence [13]. Both use a warmup by running attention fully dense while the indexer learns to imitate, then hand it control of routing. DeepSeek's warmup is short and surgical, about 1,000 steps and 2.1B tokens with everything frozen except the indexer, before the 944B-token sparse stage where the full model adapts [10]. MSA adds one more stabilizer, the always-retained local block, so the model never loses its immediate context even if the indexer misfires.

The remaining difference is when sparsity enters training, which is NSA's original question. DSA originally entered late, grafted onto a finished model through continued pretraining. MSA moved earlier, validating the recipe both ways on a mid-scale MoE, one run sparse from step zero and one converted from a dense checkpoint. Both matched the full-attention baseline, with the native run slightly ahead on retrieval-heavy long-context evals [13]. The newest adopters push the same direction from the other end. GLM-5 still added DSA to a trained base, but the conversion that cost DeepSeek the better part of a trillion tokens took Zhipu a much shorter warm-up [16]. Sparsity is moving toward the start of training.

## The payoff

The efficiency numbers deserve a little care, because three different MSA figures are floating around and they measure different things. The 28.4x figure is algorithmic, measuring how much MSA reduces per-token attention compute on paper at 1M context [13]. The kernel figures are what that becomes in wall-clock terms once the memory system has its say, with the co-designed kernel reaching 14.2x on prefill and 7.6x on decode on H800 [13]. And the model-level comparison is between products rather than kernels, where M3 runs roughly 9x faster prefill and 15x faster decode than the full-attention M2 at 1M [16].

The kernel work is therefore half the story, with two ideas doing most of the work. The first is exp-free top-k. Softmax preserves ordering, so ranking raw scores gives identical indices while skipping the max, exp, and sum entirely. At 128K with k=16 it runs 5.1x faster than torch.topk [13]. The second is KV-outer sparse attention, which inverts the usual loop structure by iterating over KV blocks, gathering the queries that selected each block, and reading every block exactly once with contiguous access. MiniMax reports over 4x versus open-source baselines like Flash-Sparse-Attention and flash-moba, with FP8 and NVFP4 paths in the released kernel [12][17]. On the DSA side the payoff also showed up in the API bill, as DeepSeek cut prices substantially alongside V3.2-Exp [18].

If there's a lesson in this cycle, it's probably that the algorithm and the kernel have to be designed together. A 28x compute reduction on paper only becomes a real speedup when the memory access pattern cooperates.

## Where it's heading

Back to the framing question, who decides and at what granularity. Two trends look solid as selection is getting more learned (static patterns survive as complements, not full answers), and it's entering training earlier (retrofit, then from-scratch validation, and presumably native-by-default next). The granularity axis is still somewhat in dispute. Blocks may win on deployability today, since tensor cores want contiguous memory, but token-level selection is the more precise instrument, and DSA's spread through the GLM line suggests fine granularity can be made hardware-friendly with enough kernel optimization. I'd bet selection gets finer as the kernels mature, not coarser. Meanwhile the other branch of the fork keeps folding linear layers into full-attention stacks, and with K3 it now has a frontier-scale flagship of its own. My guess is the two camps trade ideas rather than one eliminating the other. Kimi's full-attention layers are already MLA, the exact substrate DSA sparsifies, so a stack that runs KDA-style linear layers for most of its depth and a learned indexer on the remaining full-attention layers doesn't seem far-fetched.

There's a quieter trendline underneath all of this, as the direction of design is reversing. Attention used to be specified on paper and handed to kernel engineers afterward. In this generation the causality runs the other way. MSA's blocks are 128 tokens because that's the shape tensor cores eat, its top-k was rebuilt to avoid the exponential, DSA's indexer was FP8 from the start, and GLM-5.2 added IndexShare because the indexer became a bottleneck at 1M. The architectures are being designed backwards from the silicon, whereas the next attention mechanism will probably be negotiated with the memory system.

One last open question centers around the fact that the indexer today feels like an afterthought, a couple of projection matrices, a max-pool, an FP8 kernel, and the work on it so far pushes toward making it cheaper (IndexShare being the latest example) rather than more capable. But functionally it's a small learned retrieval system sitting inside every attention layer, and the opposite experiment, giving it real capacity rather than shaving its cost, still looks open. If context really is becoming another dimension we scale, the thing that decides what to read from that context might turn out to be worth spending real parameters on.
