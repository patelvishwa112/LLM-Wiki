Why does an agent that's genuinely smart still ship the wrong thing, over and over, on the exact same codebase?
Follow my Substack to get fresh AI alpha:substack.com/@0xMortyx
Not because the model is weak. Because "vibe coding," typing loose intent and letting the agent fill in the gaps, breaks in three specific, well-documented ways once you move past toy projects. Every major AI coding tool spent 2025 and 2026 building an answer to those three breaks. That answer now has a name: spec engineering, and it's the discipline of writing the specification itself as the real artifact, with the code as something generated and checked against it.
GitHub, AWS, and a wave of new tools (Spec Kit, Kiro, OpenSpec, BMAD, Cursor rules, Augment Cosmos) all converged on fixing the same three things. Here's each failure, exactly how spec engineering answers it, and what the numbers actually say.
1. Intent Drift
A loose prompt lets the model guess, and its guess rarely matches what you actually wanted.
THE FIRST BREAK
"Add login" is not an instruction, it's a shape with the details missing. Which auth provider. Password rules. What happens on a failed attempt. Session length. The model has to guess at all of it, and it picks reasonable defaults that routinely aren't the ones your team actually wanted. Multiply that by every vague prompt in a real project and the codebase fills up with decisions nobody actually made.
Spec engineering's fix: write the acceptance criteria before any code exists, so the "guessing" happens once, in a document you can read and correct, instead of silently, inside generated code you have to reverse-engineer to catch.
python
VIBE PROMPT VS SPEC
# vibe coding: the model fills every gap itself
"add login"

# spec engineering: the gaps are closed before code exists
Requirement: email + password auth, 5 failed attempts = 15min lock
Acceptance: session expires after 24h, refresh token rotates
Out of scope: social login, 2FA (phase 2)
✓ The guessing happens once, on paper, where you can catch it
2. Context Decay
Past a certain codebase size, the agent forgets earlier decisions and quietly contradicts them.
THE SECOND BREAK
Every model has an effective context window, and every real codebase eventually grows past what fits comfortably inside it. When that happens, the agent doesn't error out, it just quietly stops remembering the decision from three weeks ago and picks a different, often incompatible, approach today. The bug doesn't look like a bug. It looks like two reasonable pieces of code that don't agree.
Spec engineering's fix: keep the decisions in a durable, structured document the agent re-reads every session, instead of hoping they survive in a context window that's constantly being evicted and summarized.
python
WHAT DECAYS VS WHAT PERSISTS
# conversation-only memory: decisions live in the chat
"we decided to use JWT, not sessions" → said once, week 1
# ...by week 6, past the context window, it's gone

# spec engineering: decisions live in the spec, re-read every time
auth.spec.md → "Session strategy: JWT. Do not use server sessions."
# still there, still enforced, on session 60
✓ Decisions live in a document the agent re-reads, not a chat it forgets
3. Unverifiable Output
Without written acceptance criteria, nobody, human or agent, can say whether the code is actually right.
THE THIRD BREAK
"Does this work?" is a different question from "does this match what we needed?" Vibe-coded output can pass every test you happened to think of and still miss the requirement entirely, because there was never a written definition of done to check it against. That's when code review turns into an open-ended argument instead of a checklist, and it's the failure mode that scales worst as a team grows.
Spec engineering's fix: acceptance criteria written before the code, specific enough that passing or failing them is a fact, not an opinion. Some tools go further and use formal logic or SMT solvers to catch contradictions in the spec itself before any code gets generated.
python
OPINION VS FACT
# unverifiable: "does this look right to you?"
# every reviewer answers differently, review never ends

# spec engineering: acceptance criteria, checked as fact
GIVEN 5 failed login attempts
WHEN the 6th attempt is made
THEN the account locks for 15 minutes
# passes or fails. no opinion required.
The honest caveat here:A markdown spec that nobody re-verifies against the code drifts too, just slower than a prompt does. The tools that actually solve this keep the spec "living," checked against the real system, not a document written once and trusted forever.
