Memory Engineering: Memory Is a Forgetting Policy, Not a Store

When an engineer first gives an agent memory, they build remembering. A store where facts about the user, history, and drawn conclusions accumulate. It looks solved: the more the agent remembers, the smarter it is. A month in, the memory has swelled to thousands of records, half of them contradict each other, retrieval drags year-old junk into the context, and the agent that "has memory" answers worse than one without. Remembering was built. Forgetting was forgotten.
That is the whole point. Memory is not a store where more saved means richer. It is a flow in which experience enters, consolidates, lives a bounded time, and leaves. A store without forgetting is not memory, it is a dump that grows until it chokes itself. Human memory is good not because it remembers everything but because it forgets almost everything with virtuosity, keeping a thin layer of what is worth carrying forward. An engineer who builds only remembering builds half a system, and the other half takes revenge.
This article is a direct continuation of the context conversation. There the thesis was "the main skill is not what to put in the window but what to cut." Here it is the same, shifted in time: the main skill of memory is not "what to remember" but "what to let vanish, and when." Context is managing attention in the moment, memory is managing forgetting over time. In both, engineering is the discipline of cutting, not accumulating.
Memory is not one thing but four shelves with different lifetimes
The first mistake is treating memory as one bucket. In fact it is four different types, and confusing them means granting eternal life to what should have died in a minute, and erasing what should have lived for years.
Working memory is the current task: what the agent is doing right now, intermediate results, a draft of reasoning. It should die with the end of the turn, and trying to save it is a direct route to clutter. Episodic memory is what happened: specific events, "the user reported a 504 error on Tuesday." It lives days, decays, and consolidates. Semantic memory is durable facts extracted from episodes: "the user is on the Pro plan," "region EU." It lives long, until contradicted. Procedural memory is how to do things: skills, learned action sequences, "to close a billing ticket, first check the payment status." It lives longest and barely fades.
All engineering starts with one question, which is asked not as "store it?" but as "which shelf, and how fast does this shelf forget?" The same fact on the working shelf and on the semantic shelf is the same text with opposite lifetimes. Choosing the shelf is choosing the forgetting. Dumping everything into one bucket means refusing that choice, and then the system forgets at random: the important washes out alongside the junk.

# memory is not one store but shelves with different life policies
from enum import Enum
from dataclasses import dataclass
import time

class Shelf(Enum):
    WORKING    = "working"      # seconds, dies with the turn
    EPISODIC   = "episodic"     # days, decay + consolidation
    SEMANTIC   = "semantic"     # long, until contradicted
    PROCEDURAL = "procedural"   # longest, skills

# the lifetime is wired into the shelf, not into individual records
TTL = {
    Shelf.WORKING:    60,           # 1 minute
    Shelf.EPISODIC:   14 * 86400,   # 14 days
    Shelf.SEMANTIC:   365 * 86400,  # a year, refreshed on confirmation
    Shelf.PROCEDURAL: None,         # no expiry, lives until replaced
}

@dataclass
class Memory:
    text: str
    shelf: Shelf
    created: float
    last_used: float
    confidence: float               # how sure we are, drives eviction
The point of this code is that the TTL is wired into the shelf, not invented for each record. The moment you put a fact on the episodic shelf, it automatically inherits that shelf's lifetime and its forgetting rules. The engineer does not decide each record's fate by hand, they decide once how each shelf forgets, and from there it runs itself. That is the shift of focus from remembering to policy.
Consolidation: raw experience is not yet memory
The second mistake is writing raw experience into memory as is. The full dialogue turn, the whole tool result, the entire message. It is expensive, noisy, and does not survive retelling: a week later you pull two hundred tokens of pleasantries from memory with one fact hidden inside.
Raw experience must pass through consolidation before it becomes memory. Consolidation is compressing an episode into an extracted fact: from "the user wrote at length about everything crashing and at the end mentioned a 504 error on billing at 14:32" remains "billing endpoint: 504 error, 14:32, reproducible." It is the same move as compressing history in the context article, but with a different horizon: there we compressed for the current window, here for the future.
python
def consolidate(raw_episode: str, call_model) -> list[Memory]:
    # do NOT write raw experience as is, extract durable facts from it
    prompt = f"""Extract durable facts from this interaction.
Keep only what will matter in a week. Drop pleasantries, filler, and
anything specific to this one turn. Each fact one line, atomic.

INTERACTION:
{raw_episode}

Output facts, one per line, or NONE if nothing durable."""
    facts = call_model(prompt, temperature=0).strip().splitlines()
    now = time.time()
    out = []
    for f in facts:
        if f.strip() and f.strip() != "NONE":
            # the extracted fact goes to the episodic shelf, not working
            out.append(Memory(text=f.strip(), shelf=Shelf.EPISODIC,
                              created=now, last_used=now, confidence=0.7))
    return out
The key instruction here is "keep only what will matter in a week." That is a forgetting filter built into the moment of writing. Most experience does not survive that question, and rightly so: it should not enter memory at all. Consolidation is the first line of forgetting, the cheapest one, because what is never saved costs nothing to store and nothing to evict later. An agent that consolidates on the way in pays several times less for memory than one that writes everything and evicts afterward.
Forgetting: three mechanisms that run continuously
Here is the half almost everyone skips. Forgetting is not "we will clean the store someday," it is an active process running constantly through three different mechanisms. Without them memory grows linearly with time, and retrieval quality falls, because the signal drowns in accumulated junk.
The first mechanism is expiry by TTL. Each shelf has its own term, and a record that outlived it without being touched leaves. This is the dumbest and most reliable forgetting: time passed, no access, therefore not needed.
The second is eviction by value, when a shelf overflows. If semantic memory hit its limit, what leaves is not the oldest but the least valuable: rarely used, low confidence, long unconfirmed. This is eviction by importance, not by age.
The third, the subtlest, is superseding the stale, when a new fact contradicts an old one. "Region EU" arrives after "region US," and the old fact is not just added alongside, it must be replaced, or memory will hold two contradicting facts and feed the agent now one, now the other.
python
def forget(store: list[Memory], limits: dict) -> list[Memory]:
    now = time.time()
    survivors = []
    for m in store:
        ttl = TTL[m.shelf]
        # MECHANISM 1: expiry by TTL (no access)
        if ttl is not None and (now - m.last_used) > ttl:
            continue                      # term is up, forget
        survivors.append(m)

    # MECHANISM 2: eviction by value when a shelf overflows
    for shelf, cap in limits.items():
        on_shelf = [m for m in survivors if m.shelf == shelf]
        if len(on_shelf) > cap:
            # value = access recency * confidence
            on_shelf.sort(key=lambda m: (now - m.last_used) / max(m.confidence, 0.1))
            keep = set(id(m) for m in on_shelf[:cap])   # keep the valuable
            survivors = [m for m in survivors
                         if m.shelf != shelf or id(m) in keep]
    return survivors

def supersede(store: list[Memory], new: Memory, conflicts_with) -> list[Memory]:
    # MECHANISM 3: a new fact EVICTS the contradicting old one, not lies beside it
    out = [m for m in store if not conflicts_with(m, new)]
    out.append(new)
    return out
The three mechanisms answer three different questions, which is why all three are needed. TTL asks "how long since this was touched." Eviction asks "is this worth its space compared to the rest." Supersede asks "has this gone stale." Remove any one and memory breaks in its own way: without TTL it hoards the dead, without eviction it overflows, without supersede it contradicts itself. Forgetting is not one button, it is a discipline of three continuously running rules.
Retrieval: memory is useless if it surfaces the wrong thing
Memory exists for one moment: when, for the current query, the relevant must be surfaced from it into the context. And here the link to context engineering becomes literal: retrieved memory is another layer of the window, and it obeys the same budget and the same cutting discipline. Pulling everything remotely related from memory dilutes the window exactly the way we learned not to.
python
def recall(query: str, store: list[Memory], budget_tokens: int,
           count_tokens) -> list[Memory]:
    now = time.time()
    scored = []
    for m in store:
        rel = relevance(query, m.text)        # semantic closeness to the query
        # recency and confidence lift a fact, age sinks it
        recency = 1.0 / (1.0 + (now - m.last_used) / 86400)
        score = rel * (0.6 + 0.4 * recency) * m.confidence
        scored.append((score, m))

    scored.sort(reverse=True, key=lambda x: x[0])

    picked, used = [], 0
    for score, m in scored:
        if score < RECALL_FLOOR:              # below the floor, do not take at all
            break
        cost = count_tokens(m.text)
        if used + cost > budget_tokens:       # the memory budget in the window is finite
            break
        m.last_used = now                     # access extends life
        picked.append(m)
        used += cost
    return picked
Two details tie memory to context. The RECALL_FLOOR threshold: if a fact is not relevant enough to the query, do not surface it, because irrelevant memory in the window is the same attention-stealing noise as an irrelevant document. And m.last_used = now: the very act of access extends the record's life. This closes the loop between forgetting and use: what is retrieved lives, what is not retrieved quietly expires by TTL. Memory settles on its own toward what is actually used, and the unused drops out because no one touches it and TTL finishes it off.
How memory systems break
Memory without forgetting has its own recognizable deaths, and nearly all are a failure of the forgetting policy.
Bloat. Symptom: memory grows linearly with time, retrieval is slow, junk crawls into the context. Cause: everything is written, nothing consolidated, nothing evicted. Cure: consolidation on the way in, TTL on shelves, eviction by value.
Rot. Symptom: the agent acts on a stale fact, "writes to the old address." Cause: a new fact was laid beside the old instead of superseding it. Cure: supersede on conflict, a new fact replaces the contradicting one rather than coexisting with it.
Contradiction. Symptom: the agent answers one question differently depending on which duplicate surfaced. Cause: two conflicting facts live at once. Cure: the same supersede plus confidence, on conflict the fresher and confirmed one wins.
False immortality. The subtlest one. Symptom: a working draft that should have died with the turn got stuck in semantic memory and surfaces a month later as a "fact." Cause: put on the wrong shelf, an eternal term given to a temporary thing. Cure: explicit shelves with wired-in TTL, working memory physically cannot outlive the turn.
The first three are cured by the three forgetting mechanisms. The fourth is cured by choosing the right shelf on the way in. But the root is one: something that should have vanished remained, because forgetting was not engineered alongside remembering.
The order that works
Building memory, design forgetting at the same time as remembering, not after. First separate the shelves with different lifetimes, so each fact gets the right horizon. Then consolidate on the way in, raw experience is not written, an extracted fact is, one that passed the "matters in a week?" filter. Then turn on all three forgetting mechanisms at once: TTL, eviction by value, supersede on conflict. Then build retrieval as another layer of the context budget, with a threshold and life extension on access. And only then grow the volume, once the forgetting policy already keeps the system in shape.
Jumping ahead, hoarding memory with no forgetting in hope of sorting it out later, is exactly how "smart" agents dumb down over a month. A dump does not become memory however much it grows, it only answers slower and dirtier.
And the final thought, the reason for all of it. Memory feels like accumulation: save the agent more and it grows wiser. In fact it is selection over time: let most experience vanish, and the thin layer that remains becomes what actually makes the agent smarter tomorrow. Good memory is not the one that remembers everything but the one that forgets well, keeping exactly what is worth carrying forward. Build forgetting with the same care you build remembering, because memory is not what you store, it is what you deliberately let go.
